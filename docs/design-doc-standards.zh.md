# 设计文档规范（farvoo-fatura）

> **状态：定稿**  
> **适用范围：** `docs/**/*.md`、`**/SCHEMA.md`、`**/migrations/*.sql`，以及会话中对上述内容的解释  
> **配套规则：** `.cursor/rules/design-doc-standards.mdc`（alwaysApply）

本文解决：设计口径含糊、字段合并书写、文档与 DDL 不一致、P0 不拍板导致「自说自话」。

---

## 1. 权威顺序

发生冲突时，以下列顺序为准（前者覆盖后者）：

1. **已执行/已提交的 DDL**（`apps/fiscal-agent/internal/fiscal/store/migrations/*.sql`）
2. **库表设计权威文**（当前为 `docs/fiscal-sqlite-schema.zh.md`）
3. **包内速查**（`SCHEMA.md`）——只能摘要，不能另搞一套列定义
4. **会话中的口头说明**——若与 1/2 冲突，必须改 1 或 2，禁止只改嘴

需求类长文（v0.17 等）约束业务规则；**物理列名与类型以本仓 schema 文 + DDL 为准**。

---

## 2. 文档头部（必填）

每份设计文档开头必须有：

```markdown
> **状态：** 草稿 | 定稿 | 已废弃  
> **权威：** 是 | 否（若否，写明权威文件路径）  
> **对应实现：** 路径（如 migrations/001_init.sql）；无则写「尚未落地」
```

- **草稿：** 允许 TBD，但 TBD 必须点名，禁止用含糊句冒充已定。  
- **定稿：** 与 DDL 一致；改定稿必须同步改 DDL（或先改 DDL 再改文档）。  
- **已废弃：** 文首写替代文档链接，正文勿继续演进。

---

## 3. 数据字典写法（硬性）

### 3.1 一列一行

| 允许 | 禁止 |
|------|------|
| `salt` 一行、`wrap_meta` 一行 | `salt / wrap_meta` 当作一个列名 |
| `created_at` 一行、`updated_at` 一行 | `created_at / updated_at` 挤在「列」单元格 |

类型、必填、说明分列写清：

```markdown
| 列 | 类型 | 必填 | 说明 |
|----|------|------|------|
| salt | TEXT | 否 | … |
| wrap_meta | TEXT | 否 | … |
| created_at | TEXT | 是 | … |
| updated_at | TEXT | 是 | … |
```

### 3.2 说明列必须可实现

说明里必须能回答实现者：

- 存什么（内容语义）
- 空怎么办（NULL 是否合法、默认值）
- **不是**什么（易混概念，如「不是 AES IV」）
- P0 用哪套方案（若存在多种算法）

### 3.3 禁止用「/」掩盖未定

错误示例：`password 用 AES/DPAPI 加密` 且不写 P0。  
正确示例：`P0：DPAPI 整包；备选：AES-GCM + wrap_meta.iv（非 P0）`。

---

## 4. 文档与 DDL 同步检查单

改表或改设计文时，自检：

- [ ] 设计文每一个列名都能在对应 `CREATE TABLE` 找到
- [ ] DDL 每一个用户列都能在设计文找到
- [ ] 可空、DEFAULT、UNIQUE 与文档「必填/说明」一致
- [ ] `SCHEMA.md` 若提及该表，未引入第三套列清单
- [ ] 枚举取值在文档有表，DDL 用 CHECK 或文档标明「应用层枚举」

不一致时：**先改齐再回答用户问题。**

---

## 5. 会话解释规范

解释某字段时：

1. 先读权威设计文或 DDL（禁止只靠对话记忆）
2. 回答格式：`字段名（表.列）→ 定稿用途`；若文档曾错误，先承认并指出已改正文何处
3. 举例场景服务定稿，不得举出与定稿相反的「另一种真相」而不标注「非 P0 备选」

---

## 6. 术语与命名

- 物理列：`snake_case`
- 同一概念全程一名；若需中文名，在术语表定义一次
- 密钥相关：`password_ciphertext` / `wrap_meta` / `wrapped_private_key` 等以 schema 文为准，会话勿临时改名
