| # | 定法 |

| **整桌本机分单** | **必须支持。** 云端常为 `whole_table`（客人懒得分、收银未按人拆）→ 店员在 Agent **代为按菜分单** 再按人开票。禁止「whole 只能整桌一张、不能进分配器」 |
| 云 | 分单调整与开票 **只落本机**；**不回写** Farvoo / 云端分单 |
| 开票节奏 | **分出来的人可先开**；开票成功后该份额从总池 **消去**；未开部分可继续改、继续开 |
| 数量规则 | 与 Restaurant **按菜分单**对齐（有理数：整 + 分子/分母；剩余扣减；金额分摊同算法口径） |
| 人名 | **禁止重名** |
| 同步次数 | **同一收银账单（同一 `source_sale_id`）只同步一次**；后续产品将同步绑在 **关台**。开票前「云端再推覆盖本机未开票分单」**不在本方案范围**，不做冲突策略 |
| 原桌权威 | 入库冻结 **`source_lines`（+ gross_total）**；本机分单另存 **allocation**（人 → 行键 + 有理数份额）。分配不得改源行。落库偏好：`payload_json` 冻结 + **`allocation_json`** 唯一写入（实现刀补 DDL） |
| 清草稿 | **全部未开人已开完，且剩余池为空** 才 `DeleteBillDraftsBySale`。禁止「人开完但池非空」静默删草稿 |
| 并发 | **乐观锁（OCC）**：见 §5.1。禁止无提示 last-write-wins；不做双浏览器 allocation 自动合并 |

本文在此基础上写清：**壳层依据**、**信息架构**、**状态机**、**与现有 Admin 的衔接**。

## 1. 问题陈述

店员在 Fiscal Admin 处理收银账单时，需要完成一类 **高密度操作台** 工作：

1. 看清整桌剩余菜品（总池）  
2. 把数量（含几分之几）分给人  
3. 对某人填 NIF → 签发 FT → 打印  
4. 已开部分从池中消失，继续处理下一人  

现有实现把详情塞在 **收银账单列表同页下方**（`#billDetail`），按人仅卡片列表 +「签发此人」——**没有**左池/右份额分配器。若再套一层 **小弹窗（≈520px）** 做分单，或直接 **浏览器全屏**，都会和任务不匹配。

## 2. 壳层选型：产品分析（不迎合预设）

### 2.1 候选对比

| 壳层 | 适合什么 | 对本任务 | 结论 |
|------|----------|----------|------|
| **小居中 Modal**（现商品选择器量级） | 短表单、二选一确认、单点选择 | 双栏分配 + 分数输入 + 多人进度 + NIF，视口不够，滚动地狱，且挡不住「主任务感」 | **否决** 作为分单主表面 |
| **大 Modal / 准全屏 Overlay**（80–95% 视口） | 偶尔的复杂编辑、希望保留背后列表模糊可见 | 能塞下双栏，但侧栏导航被盖住；关窗后状态易丢感；与「开一张再开一张」的长会话冲突 | **备选**，非首选 |
| **真全屏（含藏侧栏）** | 沉浸式向导、首次设置、平板 kiosk | 店员仍要看角标/切发票查询；全屏过重，退出成本高 | **否决** |
| **右侧 Drawer（~480–640px）** | 详情预览、轻量编辑（Shopify/Stripe 常见） | 单栏尚可；**左池+右份额** 放进 drawer 会挤成上下叠或极窄双栏，分数输入难用 | **否决** 作为分配器主体；可用于「仅签发确认」窄条 |
| **Main content 专用 View**（替换主区，侧栏保留） | 本产品已有范式：`新建开票` / `开票步骤` 都是主区多栏，不是弹窗 | 双栏自然；进度条与桌台上下文常驻；开完一人不必关层；与「部分开票消账」长会话一致 | **P0 首选** |

### 2.2 行业惯例（收银 / 分单 / 开票）

- **餐厅 POS 分单**（Toast / Square for Restaurants / Lightspeed 等）：拆单几乎都在 **主工作区或整页检查器**，不是小对话框。原因是：行项目多、要对照剩余数量、错误代价高（开错票）。  
- **电商后台「复杂编辑」**：Shopify 用大页或宽 drawer；真正「分配/对账」类用 **dedicated page**。  
- **本仓已有一致性**：手工开票是 `view-order-new`（主区 `.split` 双栏）→ `view-order-invoice`（主区开票），**只有选商品**用 Modal——选对了边界。收银账单应对齐这条，而不是另造一套「全塞进弹窗」。

### 2.3 壳层裁决（已定稿）

> **分单 + 进度 = 专用主区 View（侧栏保留）。**  
> **签发动作 = 同一 View 内的右侧/底部「开票条」**，而不是再弹一层大窗。  
> **破坏性确认**（丢弃整单、重名冲突）才用小 Modal。

即：不是「一切都进 main」，也不是「点击开票就全屏」——**工作面在主区，确认点仍可小弹**。

### 2.4 与「列表下钻详情」现状的关系

今天 `#billDetail` 叠在列表下方：小桌单尚可，分单分配器会把列表顶没或双滚动。  
**P0 定法：** 列表页只负责选桌；点「进入开票 / 分单」→ **导航到** `view-bill-split`（或等价 view id），返回才回列表。与「手工开票 → 新建开票页」同构。

## 3. 信息架构（P0）

```
侧栏 [收银账单]
  └─ view-bills          列表（桌号 / 范围标签 / 剩余金额 / 已开人数）
       └─ 进入 → view-bill-split   分单工作台（本文主体）
            ├─ 顶栏：桌号 · 同步来源 · 剩余合计 · 已开/未开进度 · 返回列表
            ├─ 左栏：剩余总池（未开票数量）
            ├─ 中/右：当前编辑的人（份额编辑 + 几分之几）
            ├─ 人条：多人 Tab/Chip（禁重名；已开锁定）
            └─ 开票条：该人 NIF / 名称 / 签发并打印（仅未开人可点）
```

### 3.1 三区职责（一张图说清）

| 区域 | 唯一职责 | 禁止 |
|------|----------|------|
| **左 · 剩余池** | 展示尚未开票的菜与剩余有理数数量 | 在此直接改单价/删菜（P0 不改价） |
| **右 · 当前人份额** | 从池分配到此人；输入整/分子/分母 | 编辑已开票锁定人 |
| **开票条** | 购方 + 签发 | 承担分配逻辑 |

「整桌一张开完」：**仅当剩余池 = 整桌且从未按人开过、且用户选择「整桌开票」模式** 时保留入口（见 §5 互斥）。一旦开始按人分配并开出第一张，整桌入口隐藏（现有 `scope_mutex`）。

### 3.2 初始灌入

| 同步形态 | 进入工作台时 |
|----------|----------------|
| `whole_table` | 左池 = 全部 `source_lines`；人列表空或引导「添加用餐人」→ **店员代分**（主路径之一） |
| `split` | 按云端/灌入的 allocation 初值；左池 = 源行 − 已占用；可继续改 |
| 已有部分人开票 | 已开人 **只读卡片**（票号）；其数量不回池；未开人与剩余可继续改 |

**与现实现缺口（实现刀必改）：** 今日 `IssueFromBillDraft` 对 `scope_type=whole_table` 拒绝 `mode=person`。定稿后：**whole 草稿在写过 allocation（或等价升格）后必须能 `mode=person` 签发**；未分配且用户选整桌时仍可 `mode=whole_table`（互斥见 §5）。

## 4. 交互细则（对齐 Restaurant）

### 4.1 数量（有理数）

- 输入：**整 + 分子/分母**（与 `bill-split-by-item` / `validateQtyParts` 同语义）。  
- 禁止：分母缺失、分母 0、假分数。  
- 分配合计不得超过该行剩余；超分/未分完用状态色（剩余 / 超分 / 完成），文案口径与 Restaurant 对齐（可中葡后续，P0 中文即可）。  
- 瓶/份几分之几：例如 1 瓶分给两人各 `1/2`。

### 4.2 人名

- 添加人时 trim 后做 **大小写不敏感** 重名校验（对齐 Restaurant `splitPersonKey` 一类规则）。  
- 重名：阻断保存，小提示，不静默改名。

### 4.3 从池到人

- 推荐：**选中左行 → 在右栏填数量**（或「移入当前人」+ 默认 1 / 剩余）。  
- 改右栏数量 → 左池剩余实时重算。  
- 删除某人未开份额 → 数量回到左池。

### 4.4 开票后消账

1. 校验：该人至少一行有效份额；NIF 规则同现工作台。  
2. `POST .../issue` `mode=person`（`scope_id` 见 §6）。  
3. 成功：该人标已开 + 票号；其份额 **永久离开** 可编辑池；刷新左池（理论上其人占用已不在未开分配里）。  
4. 全部人开完 **且左池为空** → 清草稿；若人开完但池非空 → **不删**草稿，UI 提示须继续分配或处理剩余。

## 5. 状态机（本机）

```
[列表 open]
    → 进入工作台
[编辑中] 可改未开分配、加人、改分数
    → 签发某人成功
[部分已开] 已开人锁定；未开可继续编辑
    → 再签发 / 或丢弃未开草稿
[全部开完且池空] 草稿删除 → 回列表（该桌消失）
[人开完但池非空] 草稿保留；须继续分配剩余或（经确认后）丢弃未开部分
```

**丢弃：** 仅未开部分放弃；已开发票保留（现 discard 语义）。产品文案：「不再处理未开部分」，避免理解成作废已开票。

**清草稿（P0，相对旧「人开完即删」）：** 自动硬删仅当 **(a)** 不存在未开票的 person scope，**且** **(b)** 相对 `source_lines` 的剩余池为空。已开进度仍以 `invoices` 业务键为准；剩余池由源行 − 已开占用 − 未开 allocation 计算。

**整桌 vs 按人互斥：** 保持 workbench §5；UI 在已存在任一张按人 FT 后禁用整桌签发。

### 5.1 并发双开 / 双改（P0 定法）

**场景：** 两浏览器（或两标签）同时改同一收银账单的 allocation / 同时点签发。店员主路径仍是单机单窗；并发是防呆，不是协同编辑。

| 项 | 定法 |
|----|------|
| **分配保存** | **乐观锁**：每次成功保存递增 `allocation_revision`（或等价 etag/`updated_at`）。客户端带「上次读到的 revision」；服务端不一致 → **409**，不覆盖。UI toast：「已被其他窗口更新，请刷新后再改」。 |
| **禁止** | 无提示 last-write-wins（后写覆盖先写且店员不知） |
| **禁止** | 双端 allocation 自动三路合并（有理数份额合并易错、代价高） |
| **签发** | 签发前服务端再读最新 allocation + 源行校验；`request_id` 含 `scope_id` 幂等（既有）。若该 `scope_id` 已有 FT → 返回原票，不重签。 |
| **签发 vs 过期 UI** | 客户端携带的 allocation revision 若已过期 → 拒签或要求刷新后再签（与保存同一套 revision），避免按过期份额开票。 |
| **已开人** | 只读；他窗开票成功后本窗靠刷新 / SSE 后禁用该人编辑。 |
| **P1 不做** | 互斥编辑锁、谁在编辑中的 presence、WebSocket 协同光标 |

**为何选 OCC 而非排它锁：** 打票机旁几乎总是单操作员；OCC 实现简单、无锁泄漏；冲突时强制刷新比静默丢改更安全（防超开/错分）。

## 6. 数据落点（P0 产品约束；实现另开刀）

| 项 | P0 定法 |
|----|---------|
| 云回写 | **不做** |
| 原桌权威 | 入库冻结 `source_lines`（+ `gross_total`）；分配 UI **不得**改源行 |
| 本机分配 | 另存 `allocation`（人 → 行键 + 有理数）；落库偏好独立列 `allocation_json` + 唯一写入入口（DDL 实现刀补） |
| 已开进度 | 仍以 `invoices` 业务键为准（workbench 既有），UI 只读叠加 |
| 清草稿 | 见 §5：人开完 **且** 池空 |
| 新人 `scope_id` | 本机生成 UUID；开票 `person` 使用该 id；**不**要求云端预先有该 split |
| `whole_table` 首次改成按人 | 写 allocation 后签发走 `person`；禁止再整桌（一旦有按人票或用户明确进入按人路径后） |

实现刀须同步修订 [`fiscal-bill-draft-workbench.zh.md`](fiscal-bill-draft-workbench.zh.md) §6 清草稿条件与映射/allocation API。

## 9.1 实现须挡的风险（摘要）

与「再同步冲突」无关、实现刀仍须处理：

| 项 | 定法 |
|----|------|
| 超开 | 相对原桌行快照校验有理数占用；超分拒签 |
| 清草稿 | 全部未开人开完 **且** 剩余池为空才删；禁止「人开完但池非空」静默清掉 |
| 原桌 / 分配 | `source_lines` 冻结；`allocation` 另存；签发校验占用 ≤ 源行 |
| 分位 | 与 restaurant 分摊口径一致；全部分完后合计对齐原桌 |

## 10. 验收（产品）

1. 列表点进入 → 主区工作台，侧栏仍在；无小弹窗承载分配器。  
2. 云端已 split 灌入后可改未开人；已开人只读。  
3. 左池随分配与开票消账实时变。  
4. ½ 瓶等分数与 Restaurant 同规则拒假分数。  
5. 重名不可添加。  
6. 先开 A 再改 B 再开 B；A 菜不回池。  
7. 刷新浏览器后未开分配仍在（本机持久化）。  
8. 全程无云回写调用。  
9. 人已开完但左池非空 → 草稿仍在；分配完池空后才自动清除。
